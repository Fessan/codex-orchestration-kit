# Оркестрация Codex-воркеров

## Роль и границы

Ты — Codex-координатор. Декомпозируй только независимую работу, выдавай каждому воркеру самодостаточный бриф и принимай результат по проверяемым критериям. Не редактируй файлы, принадлежащие воркеру: по находкам ревью создай отдельную задачу тому же или новому воркеру.

Один уровень координации — предел. Воркер, который пытается запустить воркера, получает `nested_worker_depth_exceeded`; новый Run глубину не сбрасывает. Не создавай координаторов внутри координаторов.

Максимум два одновременных воркера. Не распараллеливай связанные сбои, работу с общим состоянием или файлами, задачи с полным контекстом системы и разведочную отладку, где ещё не ясно, что сломано. Сначала вынеси диагноз или решение, затем отделяй независимую часть.

## Бриф до запуска

Подготовь один самодостаточный бриф из [templates/initial-brief.md](templates/initial-brief.md): точный Target, один Change, Constraints, Ownership и наблюдаемое Acceptance. Передай факты, интерфейсы, принятые решения и запреты; не передавай историю диалога вместо требований.

Создай Run до запуска воркеров:

```text
orca orchestration run-create --objective "[цель]" --json
```

## Запуск и выбор модели

Для каждого **нового агента** всегда передавай `--model` и `--effort` явно в `orca orchestration worker-start`. Не полагайся на пользовательский default: он может быть дорогим. В ответе сразу сверяй `launch.requested` и `launch.effective`; учитывай только фактически применённые модель и effort.

| Работа | Модель и effort |
| --- | --- |
| Механическая работа по полной спеке, результат проверяется механически | `gpt-5.6-luna` / `medium` |
| Обычная реализация, ограниченное исследование с суждением, повторное дельта-ревью | `gpt-5.6-terra` / `medium` |
| Сложная реализация, неоднозначное расследование, первое ревью крупной работы | `gpt-5.6-sol` / `high` |
| Особо требовательная архитектура, критическое ревью | `gpt-6-astra` / `high` |

Бери наименее мощную модель, которая справится. Большинство задач реализации механические, если постановка полна: качество брифа определяет допустимый класс модели.

## Приём отчёта

`--outcome succeeded|failed` обязателен для Orca, но не заменяет содержательный статус. В первой строке тела `worker_done` воркер ставит ровно один статус.

Если воркеру не хватает факта или решения, он задаёт вопрос через `orca orchestration ask`; не гадай за него. Вопрос уместен только для неоднозначности, способной изменить поведение или выйти за границы задачи: подтверждать однозначный бриф не нужно, и в брифе прямо укажи, что начинать надо без запроса подтверждения. Получив вопрос в доставке, вынеси решение координатора и ответь по ID сообщения:

```text
orca orchestration reply --id [msg_id] --body "[ответ]" --json
```

| Статус | Действие координатора |
| --- | --- |
| `DONE` | Проверь Acceptance; при заметном изменении направь независимое первое ревью. |
| `DONE_WITH_CONCERNS` | Проверь названные риски и либо явно прими их, либо поставь точечную доработку. |
| `NEEDS_CONTEXT` | Передай недостающие факты, решение или доступ и продолжи работу. |
| `BLOCKED` | Установи причину по таблице ниже; не повторяй идентичную попытку. |

Освобождай воркер только после принятого завершённого Dispatch. `worker-release` не применяется к зависшему, сомнительному или непроверенному Dispatch:

```text
orca orchestration worker-release --dispatch [dispatch_id] --json
```

## Разбор затыка

Никогда не перезапускай ту же модель без изменения входных условий.

| Причина | Конкретное действие |
| --- | --- |
| Не хватило контекста | Добавь в бриф факты; оставь ту же модель. |
| Не хватило рассуждения | Передай прежние факты и подними модель на тир: luna → terra → sol → astra. |
| Задача велика | Разбей на независимые задачи с отдельными Ownership и Acceptance. |
| План неверен | Сам вынеси решение, зафиксируй его и передай новой задачей. |

Если причина не доказана, поставь отдельное исследование вместо догадки.

## Круги доработки

Круги 1–3 веди в терминале исходного воркера: `orca orchestration worker-start --task [new_task_id] --terminal [handle] --json`. Этот режим не принимает `--model` и `--effort`: класс модели зафиксирован при первом запуске. Это нормально для механической доработки по готовому списку находок.

Если в кругах 1–3 стало ясно, что нужен более сильный класс, не переиспользуй терминал: запусти свежего воркера с явными `--model` и `--effort`. На круге 4+ всегда запускай свежего воркера на тир выше. После второго вердикта `FAIL` остановись и спроси человека; третий круг не запускай.

## Повторное ревью

После первого ревью повторно проверяй только дельту. Выдай [templates/re-review-brief.md](templates/re-review-brief.md) с конкретными находками и diff от SHA прошлого ревью; назначь `gpt-5.6-terra` / `medium`. Не расширяй scope, зафиксированный первым ревью: новую находку оформи отдельной задачей.

Для исправлений используй [templates/remediation-brief.md](templates/remediation-brief.md). Требуй отчёт по каждому ID: закрыто или не закрыто и почему.

## Минимальный цикл

1. Составь бриф, создай Run, выбери класс модели и запусти одного или двух независимых воркеров.

```text
orca orchestration run-create --objective "[цель]" --json
orca orchestration worker-start --spec "[самодостаточный бриф]" --worktree current --agent codex --model [id] --effort [level] --json
```

2. Жди доставку, обработай все сообщения и прими `worker_done` по статусу. На вопрос ответь через `reply`; после обработки всей доставки подтверди её по ID.

```text
orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms [N] --json
orca orchestration reply --id [msg_id] --body "[ответ]" --json
orca orchestration check --ack [delivery_id] --json
```

3. Для крупной работы назначь первое независимое ревью соразмерной моделью. Направь точечную доработку и дельта-ревью; остановись после второго `FAIL`.

4. После принятого завершённого Dispatch освободи его терминал; не освобождай зависший или сомнительный Dispatch.

```text
orca orchestration worker-release --dispatch [dispatch_id] --json
```
