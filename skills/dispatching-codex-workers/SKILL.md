# Делегирование воркерам (роль — координатор)

Эта роль применима, когда координируешь ты, а не когда тебя запустили как воркера. Если тебя
дисптечили через Orca с Task/Dispatch-преамбулой — ты в роли 2 из [../../AGENTS.md](../../AGENTS.md):
выполняй бриф сам, не читай этот файл как разрешение поднять своих воркеров.

Декомпозируй независимую работу, выдай каждому воркеру самодостаточный бриф, прими результат
через Orca. Не передавай воркеру историю разговора вместо требований — решения, интерфейсы,
границы и критерии приёмки должны быть в брифе.

## Когда применять

Для плана с независимыми или слабо связанными кусками реализации и отдельным ревью каждого
заметного изменения. Максимум два одновременных воркера. Не распараллеливай, если сбои связаны,
нужен полный контекст системы, это разведочная отладка (ещё не ясно, что сломано) или части
делят общее состояние, ресурсы, пересекающиеся файлы. В этих случаях сначала диагноз или
границы, затем независимые части.

## Подготовка и запуск

1. Зафиксируй базовый SHA.
2. Если бриф класса С/В опирается на допущения о существующем коде — сначала сверь их
   read-only проверкой по [../../methodology/plan-vs-code.md](../../methodology/plan-vs-code.md);
   опровержение, меняющее поведение, правит план до запуска исполнителя.
3. Подготовь один самодостаточный бриф из [templates/initial-brief.md](templates/initial-brief.md):
   `Target`, `Change`, `Constraints`, `Ownership`, `Acceptance` обязательны.
4. Создай Run и явно выбери модель и effort по
   [../../methodology/model-routing.md](../../methodology/model-routing.md). Эскалация выше
   дефолтного тира требует строки-триггера в брифе. Для диспетченного Claude-воркера явно
   повтори в брифе запрет запускать вложенных воркеров или in-session субагентов.

```text
orca orchestration run-create --objective "[цель]" --json
~/.claude/bin/ws --spec @[путь к файлу брифа] --worktree current --agent codex --model [id] --effort [level] --json
```

Запуск идёт через `ws` (не напрямую через `orca orchestration worker-start`), чтобы сработал
гейт триггеров (`high:`/`astra:`/`opus:`/`legacy:`) из
[../../methodology/model-routing.md](../../methodology/model-routing.md). `--spec @file` передаёт
бриф файлом — так же ищется строка-триггер, если она нужна. После запуска сверь `launch.effective`
в ответе: это фактически применённые модель и effort, не то, что было запрошено.

5. Жди сообщения, обрабатывай вопросы через `reply`, освобождай только принятый завершённый
   Dispatch.

```text
orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms [N] --json
orca orchestration reply --id [msg_id] --body "[ответ]" --json
orca orchestration worker-release --dispatch [dispatch_id] --json
```

`worker_done` обязан иметь `--outcome succeeded|failed`; это не заменяет содержательный статус —
он передаётся первой строкой тела.

## Приём отчёта

| Статус | Действие координатора |
| --- | --- |
| `DONE` | Проверь Acceptance; для заметного изменения — независимое первое ревью. |
| `DONE_WITH_CONCERNS` | Проверь названные риски; либо прими явно, либо оформи точечную доработку. |
| `NEEDS_CONTEXT` | Передай недостающие факты или решение, продолжи тем же терминалом. |
| `BLOCKED` | Разбери причину по таблице затыка в [../../methodology/model-routing.md](../../methodology/model-routing.md); не повторяй идентичную попытку. |

## Вопросы воркера

Вопрос через `orca orchestration ask` уместен только для неоднозначности, способной изменить
поведение или выйти за границы задачи — брифы прямо указывают начинать без подтверждения
получения. Ответь по ID сообщения и проверь, не изменился ли scope, прежде чем запускать
дальше.

```text
orca orchestration reply --id [msg_id] --body "[решение]" --json
```

## Первое ревью

Перед запуском ревью автор сохраняет работу коммитом в рабочую ветку (без push) — незакоммиченное
рабочее дерево ревью не получает. Задай координатор отдельным брифом из
[templates/first-review-brief.md](templates/first-review-brief.md): полные требования, базовый
SHA и SHA этого коммита, точный scope, строка `review-of: [dispatch id автора]`, отдельная
проверка качества тестов (см. [../../methodology/review-loops.md](../../methodology/review-loops.md)).
Предпочтительно — ревьюер из другого поставщика модели, чем автор; при недоступности — сильный
тир того же поставщика с явной пометкой в отчёте.

## Доработка и повторное ревью

Находки первого ревью — в [templates/remediation-brief.md](templates/remediation-brief.md), с
точными ID и критерием закрытия для каждого. Отчёт о доработке — по каждому пункту отдельно.
После доработки автор снова коммитит (без push) — этот коммит становится конечной точкой дельты (current_sha).

Повторное ревью — по [templates/re-review-brief.md](templates/re-review-brief.md): конкретный
список находок и diff строго `prev_review_sha..current_sha`, где `prev_review_sha` — коммит,
который видел прошлый ревьюер, а не весь проект и не исходный change-set. Оба SHA — в брифе.
Дешёвый тир того же поставщика, что первый ревьюер. После второго `FAIL` — стоп, решение
человеку; третий круг не запускай.

Точечную доработку до стоп-правила (не третий круг) можно вести в терминале исходного воркера без
нового `--model`/`--effort` (класс модели зафиксирован при первом запуске). Если стало ясно, что
нужен класс выше — не переиспользуй терминал, запускай свежего воркера с явными параметрами.

## Минимальная последовательность

1. Зафиксируй SHA, при необходимости сверь план с кодом, выбери модель, запусти одного или до
   двух независимых воркеров.
2. Прими `worker_done` по статусу, проверь Acceptance.
3. Для заметного изменения запусти первое ревью соразмерной моделью.
4. При находках — доработка и точечное дельта-ревью по правилам кругов.
5. После принятого результата освободи Dispatch через `worker-release`.
