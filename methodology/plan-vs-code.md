# Сверка плана с кодом

Планы с уверенными формулировками про существующие файлы, API и поведение расходятся с реальным
кодом чаще, чем кажется во время планирования: убедительность плана не коррелирует с его
точностью. Ошибка, обнаруженная после того, как воркер уже начал писать код по неверному плану,
стоит дороже, чем короткая проверка до начала.

## Когда применять

Перед брифом класса С или В (см. [engagement.md](engagement.md)), который опирается на
допущения о существующем коде — «этот метод уже принимает такой параметр», «этот эндпоинт уже
возвращает это поле», «эта функция уже вызывается оттуда-то». Для класса Н или для плана без
допущений о существующем коде (новый файл с нуля, чисто текстовая задача) шаг не нужен.

## Процедура

1. Из плана выписать каждое утверждение о текущем состоянии кода как отдельный пункт: файл,
   ожидаемое содержимое или поведение.
2. Read-only проверкой (дешёвой моделью — это механическая работа, не суждение) для каждого
   пункта подтвердить или опровергнуть его, указав конкретный путь к файлу и, где уместно,
   номер строки или сигнатуру.
3. Проверяющий **не правит план** — только возвращает список: пункт → подтверждён / опровергнут
   → доказательство.
4. Опровержение, которое меняет наблюдаемое поведение результата, возвращается координатору или
   человеку **до** запуска исполнителя — план правится на основе фактов, а не предположений.
   Опровержение, которое ничего не меняет в исходе (например, файл лежит на соседнем пути под
   тем же именем), можно закрыть без остановки, отметив факт.

## Что это не делает

Шаг не проверяет качество или полноту плана — только фактическую опору его конкретных
утверждений на код. Он не заменяет ревью реализации (см. [review-loops.md](review-loops.md)) и
не заменяет обратный пересказ исполнителя (см. [engagement.md](engagement.md)): пересказ ловит
неясность постановки, эта сверка — неверные факты о текущем состоянии системы.
