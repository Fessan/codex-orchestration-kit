# codex-orchestration-kit

Практическая методика делегирования: прямая Claude Code-сессия по умолчанию координирует,
Codex-воркеры реализуют через [Orca](https://github.com/stablyai/orca) — CLI, которым
координатор запускает и опрашивает изолированные сессии-воркеры (или наоборот — Codex-сессия
координирует другими Codex-воркерами напрямую). Без Orca прямая Claude-сессия реализует сама и
говорит об этом явно. Единый источник правил — [AGENTS.md](AGENTS.md), который читают оба
рантайма.

## Кому это подходит

Команде или человеку, у которых есть Codex — Claude Code рядом не обязателен, см. «Если у вас
только Codex» ниже. Orca нужна только для делегирования изолированным воркерам; без неё методика
всё равно применима к прямой сессии (нормы исполнителя, риск, ревью). Методика не про выбор
инструментов — она наводит порядок в том, кто кому что поручает, какая модель нужна для какой
работы и когда ревью пора остановить.

## Что получаете

- Единый файл инструкций [AGENTS.md](AGENTS.md) с явно разведёнными ролями: прямая сессия,
  диспетченный воркер, координатор — вместо противоречивых версий, каждая из которых по-своему
  понимает, кто редактирует код.
- Устойчивое правило выбора модели с отдельной датированной таблицей тиров
  ([methodology/model-routing.md](methodology/model-routing.md)) и техническим гейтом,
  требующим названного основания для эскалации выше дефолтного тира.
- Дисциплину ревью, где первое ревью фиксирует полный список находок, а повторное проверяет
  только дельту — вместо расширяющегося на каждом круге объёма
  ([methodology/review-loops.md](methodology/review-loops.md)).
- Протокол соразмерности риска: три класса задач (Н/С/В), где метку ставит человек, а не агент,
  и где для дорогих изменений обязательны план, независимый ревьюер и явный ответ про откат
  ([methodology/engagement.md](methodology/engagement.md)).
- Шаг сверки плана с реальным кодом до старта дорогой задачи
  ([methodology/plan-vs-code.md](methodology/plan-vs-code.md)).
- Готовые шаблоны брифов — первичный, первое ревью, доработка, повторное ревью
  ([skills/dispatching-codex-workers/templates](skills/dispatching-codex-workers/templates)).

## Установка

```sh
git clone https://github.com/Fessan/codex-orchestration-kit.git "$HOME/codex-orchestration-kit" && sh "$HOME/codex-orchestration-kit/install.sh" --user
```

Одна команда ставит симлинки только на принадлежащие комплекту имена: скиллы
`dispatching-codex-workers` и `codex-orchestration-kit` в `~/.claude/skills` и
`$CODEX_HOME/skills` (обычно `~/.codex/skills`, см. ниже), `bin/ws` в `~/.claude/bin/ws`. Это всё,
что делает `--user` сам по себе: правила методики становятся доступны обоим рантаймам как скилл и
гейт, но **не подключаются** ни к одному конкретному проекту и не становятся глобальной политикой
Codex — эти два шага отдельные и ниже.

Занятое имя — отказ с объяснением, установщик ничего не перезаписывает молча. Для проверки без
изменения реального окружения используйте `--dry-run`.

### Подключить `AGENTS.md` к проекту

`--project` можно давать и отдельно, без `--user` — тогда ставится только симлинк
`/path/to/project/AGENTS.md -> .../codex-orchestration-kit/AGENTS.md`, без скиллов и `bin/ws`:

```sh
sh "$HOME/codex-orchestration-kit/install.sh" --project /path/to/project
```

Вместе с `--user` та же ссылка ставится заодно со скиллами, гейтом и остальными правилами
комплекта:

```sh
sh "$HOME/codex-orchestration-kit/install.sh" --user --project /path/to/project
```

Симлинк кладётся только если в проекте своего `AGENTS.md` ещё нет. Если он уже есть, установщик
откажется с конфликтом и ничего не тронет: добавьте ссылку на методику вручную — либо симлинком
на другой путь, либо разделом-ссылкой в существующем `AGENTS.md` проекта (`См. также:
codex-orchestration-kit/AGENTS.md`).

Снять только эту ссылку, не трогая остального: `install.sh --uninstall --project DIR`.

**Проверка, что рантайм действительно видит правила:** откройте проект и в Codex, и в Claude Code
и спросите «какие правила из AGENTS.md ты видишь?» — оба должны процитировать роли или
маршрутизацию моделей из этого файла. Если нет — симлинк не создан или рантайм не читает
`AGENTS.md` из этого каталога.

Глобально для **Codex** методику можно подключить отдельным флагом `--with-global-agents` (ниже) —
тогда правила видны в любом проекте без `--project`. **Claude Code** глобально `AGENTS.md` не
читает — только `~/.claude/CLAUDE.md`; чтобы правила были видны во всех проектах и там, ссылку
подключают вручную (см. «Чтобы методика работала во всех проектах» ниже), это не делает
установщик.

### Флаги `install.sh`

| Флаг | Действие |
| --- | --- |
| `--user` | Основная установка: симлинки скиллов и `bin/ws` в `~/.claude` и `$CODEX_HOME`. |
| `--source DIR` | Взять комплект не из каталога, где лежит `install.sh` (умолчание), а из указанного. |
| `--project DIR` | Симлинк `DIR/AGENTS.md` на `AGENTS.md` комплекта — только если в `DIR` своего `AGENTS.md` нет. Можно отдельно от `--user` (тогда без скиллов и гейта) или вместе с ним. |
| `--with-global-agents` | Дополнительно: симлинк `$CODEX_HOME/AGENTS.md -> AGENTS.md` репозитория — только если путь свободен. Не входит в `--user` по умолчанию, потому что затрагивает глобальную политику Codex, а не только эти скиллы. Для Claude Code этот флаг ничего не делает — глобальное подключение там ручное, см. «Чтобы методика работала во всех проектах». |
| `--dry-run` | Показать, что будет сделано, без записи на диск. |
| `--uninstall` | Снять только свои ссылки: скиллы, `bin/ws`, глобальную ссылку `AGENTS.md` (если она наша) и, при повторном указании `--project DIR`, ссылку в этом проекте. Чужие файлы и симлинки на другие источники не трогает. |

`$CODEX_HOME` — переменная окружения Codex; если не задана, используется `~/.codex`. Все пути
Codex в этом README (`skills`, `AGENTS.md`) — относительно неё, а не жёстко `~/.codex`. Проверить
фактический путь: `echo "${CODEX_HOME:-$HOME/.codex}"`.

### Чтобы методика работала во всех проектах

**Codex** читает `AGENTS.md` глобально сам, если подключить его установщиком:

```sh
sh "$HOME/codex-orchestration-kit/install.sh" --user --with-global-agents
```

Ссылка `$CODEX_HOME/AGENTS.md -> AGENTS.md` репозитория ставится, только если путь свободен.

Если путь уже занят личным или корпоративным `AGENTS.md` — **не заменяйте его вручную** ссылкой
на этот репозиторий: сторонние инструменты могут дописывать в этот файл, и все его правила,
которых нет в комплекте, пропадут без предупреждения. Импорта одного файла правил в другой у
Codex нет. Вместо замены подключайте методику точечно через `--project` к нужным проектам либо
вручную перенесите нужные разделы личного файла в общий.

**Claude Code** глобальный `AGENTS.md` не читает — читает только личный `~/.claude/CLAUDE.md`.
Установщик личные файлы не редактирует, поэтому подключение ручное: одной строкой в
`~/.claude/CLAUDE.md`

```
@/path/to/codex-orchestration-kit/AGENTS.md
```

(путь — до вашего клона репозитория). После этого в каждом проекте правила видны без
`--project` и без отдельного `CLAUDE.md`-прослойки в проекте — она не нужна: Claude Code уже
читает и глобальный `~/.claude/CLAUDE.md`, и подключённый в проекте `AGENTS.md`.

## Если у вас только Codex

Claude Code рядом не нужен — методика работает и с одним Codex.

- Codex вместе с Orca: координирует сама Codex-сессия (скилл
  `skills/codex-orchestration-kit/SKILL.md`) — те же роли, гейт `ws`, классы риска Н/С/В,
  шаблоны брифов и ревью по коммитам, что и с Claude Code.
- Codex без Orca: прямая сессия делает всё сама, без делегирования — но правила из `AGENTS.md`
  (нормы исполнителя, риск, ревью) применимы и здесь.
- Что теряется: предпочтение ревьюера другого поставщика модели (`methodology/model-routing.md`,
  `methodology/review-loops.md`) — здесь его не из чего собрать, только один поставщик. Первое
  ревью тогда ведёт более сильный тир того же поставщика (необязательно та же модель — например
  Astra вместо Sol), и отчёт об этом явно говорит — это слабее, потому что модели одного
  поставщика склонны к похожим слепым пятнам.
- Установка та же: `sh install.sh --user` ставит скиллы и в `$CODEX_HOME/skills` (обычно
  `~/.codex/skills`, см. выше), и в `~/.claude/skills`. Гейт `~/.claude/bin/ws` нужен только при
  координации через Orca — без неё (режим «Codex без Orca» выше) он не используется. Если Claude
  Code не установлен, ссылки в `~/.claude` просто не используются — вреда от них нет.
- Установка не подключает `AGENTS.md`: сам `--user` не привязывает правила ни к проекту, ни
  глобально к Codex (см. «Установка» выше) — добавьте `--project` или `--with-global-agents`,
  иначе нормы риска и ревью не действуют.

## Как устроен цикл

```text
человек → карточка задачи (для С/В)
        → координатор: бриф + выбор модели + (для С/В) сверка плана с кодом
        → воркер: реализация → пакет свидетельств
        → координатор: первое ревью (полный scope) → находки?
              да → доработка → повторное ревью (только дельта) → повтор до PASS или 2×FAIL
              нет → приёмка
        → человек: пересказ (для С/В) → принято
```

Диспетченный воркер никогда не поднимает своего воркера — уровень вложенности один. Это
договорённость в инструкциях ([AGENTS.md](AGENTS.md)), а не техническое ограничение: команда
запуска сама по себе глубину не проверяет. Подробный жизненный цикл команд Orca (`run-create`,
`worker-start`, `check`, `ask`/`reply`, `worker_done`, `worker-release`) не дублируется в этом
README — актуальный гайд выдаёт сам бинарь Orca.

Когда координирует не Claude Code, а сама Codex-сессия («Codex-воркеры напрямую» выше), Claude
Code в этой конкретной цепочке не участвует вовсе — набор правил (`AGENTS.md`) от этого не
меняется, читают его оба движка одинаково.

## Риск и эскалация — коротко

Три класса риска Н/С/В различает один проверочный вопрос: «если это окажется неверным, откачусь
за десять минут или буду переделывать неделю?» Неделя — класс В (архитектура, миграции, права,
деньги, внешняя запись); опечатка или правка под существующими тестами — Н; всё среднее, что
меняет поведение, — С. Полные критерии и гейты по классам —
в [methodology/engagement.md](methodology/engagement.md).

После второго подряд `FAIL` в ревью-цикле третий круг не запускается автоматически — стоп, и
дальше решает человек.

Триггер эскалации модели — одна строка с причиной, например `high: отладка живой ошибки в
продакшене`. Основанием не считается формулировка «на всякий случай»: гейт (`bin/ws`) требует
назвать, что именно делает задачу дороже дефолтного тира, а не задним числом оправдать дорогой
выбор.

## Почему так

- **Повторные полные ревью — самый дорогой из скрытых расходов.** Каждый круг, который заново
  читает весь diff вместо конкретного списка находок, стоит непропорционально своей пользе;
  дельта-ревью на дешёвом тире закрывает тот же вопрос дешевле.
- **Эскалация модели без названной причины становится невидимой стоимостью.** Удобно не
  указывать модель явно — тогда каждый новый воркер молча наследует дорогой дефолт, и цена
  решения перестаёт быть видна тому, кто его принял.
- **Делегирование без карточки и пересказа стирает понимание проекта у человека.** Зелёные
  тесты подтверждают отдельное свойство кода, а не то, что человек удержал в голове, что и
  зачем поменялось.
- **Уверенный план — не то же самое, что план, совпадающий с кодом.** Допущение о существующем
  API или поведении, не сверенное с файлами, — частый источник работы, которую придётся
  переделывать после первого ревью, а не до него.
- **Тесты, не привязанные к требованию, ничего не доказывают.** Тест, который проходит и без
  проверяемой строки логики, даёт ложное чувство покрытия — находка про такой тест дешевле,
  чем баг, который он должен был поймать.
- **Роль координатора теряется незаметно, если он начинает писать код «раз уж смотрит».**
  Смешение роли реализатора и роли координатора в одной задаче убирает именно ту границу
  ответственности, ради которой делегирование вообще имело смысл.

## Границы

Методика не гарантирует, что делегированная реализация окажется верной, что тесты покрывают всё
нужное, что классификация риска всегда точна или что человек, подтвердивший пересказ, удержит в
памяти весь проект. Она задаёт процедуру, которая делает эти риски видимыми и проверяемыми, а не
устраняет их. Установщик не подключает `AGENTS.md` ни к одному проекту и не меняет глобальную
политику Codex автоматически — это отдельные флаги (`--project`, `--with-global-agents`) и только
на свободный путь; глобальное подключение для Claude Code установщик не делает вовсе — это
ручная строка в личном `~/.claude/CLAUDE.md` (см. «Чтобы методика работала во всех проектах»).

## Состав

```text
AGENTS.md                                    — общий источник правил для Codex и Claude Code
methodology/                                 — роли, модели, ревью, риск, сверка плана с кодом
skills/dispatching-codex-workers/            — координатор Claude Code + общие шаблоны брифов
skills/codex-orchestration-kit/              — координатор: сама Codex-сессия
bin/ws                                       — гейт эскалации модели перед запуском воркера
install.sh, tests/                           — установка симлинками и её проверка
```
