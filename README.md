# Как уменьшить расход токенов в оркестрации Codex-воркеров

## Проблема: расход уходит не туда, где его ждут

Когда несколько задач ведутся через воркеров, заметной становится не цена отдельного ответа, а цена незавершённого цикла. Дорогая модель может быть назначена на механическую доработку, а новый контекст — подниматься там, где уже есть терминал с нужными фактами. В результате расход растёт не из-за сложности результата, а из-за способа организации работы.

Один обезличенный рабочий день даёт показательный срез: 45 сессий использовали 5,93 млн некэшированных input-токенов. На две самые дорогие модели пришлось 92% расхода, а 38% — на одну задачу. Один раздел этой задачи прошёл три круга ревью и стоил около 1,44 млн токенов; третий круг оказался дороже первоначальной реализации. На дешёвые модели пришлось только 8% расхода.

Эти цифры не доказывают, что дорогие модели не нужны. Они показывают, что выбор модели и форма цикла часто важнее числа задач.

## Откуда берётся перерасход

Первая причина — перезапуск сессии вместо продолжения. Если список замечаний уже сформирован, новый воркер заново читает постановку, код и историю. Продолжение в терминале исходного воркера сохраняет контекст и обычно подходит для точечной доработки.

Вторая причина — ревью, которое на каждом круге расширяет scope. Первое ревью должно зафиксировать область и список находок. Повторная проверка отвечает только на вопрос, закрыты ли они в дельте после базового SHA. Иначе каждый круг превращается в новое полное исследование, а число токенов растёт быстрее ценности находок.

Третья причина — топовая модель по умолчанию. Удобное правило «не указывать модель» делает цену невидимой: каждый новый воркер наследует настройки пользователя. Когда реализация хорошо задана и результат проверяется командой, это часто избыточный класс модели.

## Практическая схема

Начинайте с маршрутизации. Механическую работу по полной спецификации направляйте на `gpt-5.6-luna` / `medium`. Обычную реализацию, ограниченное исследование и повторное дельта-ревью — на `gpt-5.6-terra` / `medium`. Сложную реализацию, неоднозначное расследование и первое ревью крупной работы — на `gpt-5.6-sol` / `high`. Особо требовательную архитектуру и критическое ревью оставляйте для `gpt-6-astra` / `high`.

Принцип простой: выбирайте наименее мощную модель, которая достоверно справится. Это не экономия за счёт качества. Это отказ платить за рассуждение там, где достаточно исполнить ясную последовательность и проверить результат.

Явно передавайте модель и effort при запуске нового агента и сверяйте фактическое применение в `launch.effective`. У продолжения в существующем терминале эти флаги недоступны: модель выбрана при первом запуске. Поэтому первые три круга доработки можно оставить тому же воркеру, если он закрывает конкретные замечания. Когда нужен класс выше, запускайте нового воркера с явными параметрами.

После первого ревью сохраняйте SHA и перечень находок. Повторному ревьюеру дайте только этот список и diff от базового SHA; для него достаточно `gpt-5.6-terra` / `medium`. Если повторный вердикт второй раз `FAIL`, остановите цикл и вынесите решение человеку. Третий круг без нового решения обычно воспроизводит ту же неопределённость за новую цену.

## Качество постановки определяет класс модели

Хороший бриф снижает требуемую мощность. В нём есть точная цель, один ожидаемый результат, ограничения, владение файлами и наблюдаемые критерии приёмки. Добавьте факты и принятые решения, без которых исполнитель будет исследовать систему заново.

Неполный бриф превращает даже простую задачу в исследование: модель выбирает варианты, ищет контекст и спорит с неявными ограничениями. Полный бриф, наоборот, делает большую часть реализации механической. Поэтому улучшение постановки — прямой способ перевести работу на менее дорогой класс без снижения качества.

## Что измерять и как начать

Не оценивайте процесс по расходу за день. Дни бывают тяжёлыми и лёгкими, поэтому абсолютная дневная цифра обманывает. Считайте стоимость одной завершённой задачи: входные токены всех её реализаций, доработок и ревью, делённые на число принятых результатов.

Для первого замера выберите несколько завершённых задач. Для каждой запишите число запусков, класс модели, число кругов доработки, число полных и дельта-ревью и суммарные токены. Затем отметьте, где создавался новый контекст, где scope ревью расширялся и где модель наследовала default. Этого достаточно, чтобы выбрать первую точку изменения: обычно это явная модель на новых запусках или переход повторного ревью на дельту.

Через следующий сопоставимый набор задач сравните не дневную сумму, а стоимость завершённой задачи и долю повторных полных ревью. Так будет видно, уменьшился ли расход без потери качества результата.

## Установка

Нужны Codex и Orca. Скопируйте каталог комплекта в `~/.codex/skills/<имя>/`, затем начните новую Codex-сессию и попросите её скоординировать или делегировать работу через Orca. Если инструкция подхватилась, брифы будут содержать Target, Change, Constraints, Ownership и Acceptance, а для нового агента будут явно выбраны модель и effort.

## Состав

- `SKILL.md` — рабочая инструкция Codex-координатору: полный цикл команд, выбор модели, статусы отчёта, разбор затыка, круги доработки и дельта-ревью.
- `templates/initial-brief.md` — первичный бриф воркеру.
- `templates/remediation-brief.md` — бриф точечной доработки по находкам.
- `templates/re-review-brief.md` — бриф повторного дельта-ревью.

Кому подходит: командам, у которых есть Codex и Orca, а координатором выступает Codex-сессия.
