# Оркестрация Codex-воркеров (координатор — сама Codex-сессия)

Вариант для случая, когда координатор — не Claude Code, а сама Codex-сессия, работающая
напрямую с человеком. Если координирует Claude — используй
[../dispatching-codex-workers/SKILL.md](../dispatching-codex-workers/SKILL.md): механика та же,
шаблоны брифов общие для обоих вариантов, различается только то, кто держит роль координатора.

Общая политика ролей и границ — в [../../AGENTS.md](../../AGENTS.md).

## Роль и границы

Загрузи этот скилл, только если работа делится на независимые части и ты не сама выполняешь
бриф другого координатора. Если тебя дисптечили как воркера — этот скилл неприменим: выполняй
свой бриф сам, не поднимай вложенных воркеров. Один уровень координации — предел; воркер,
пытающийся запустить воркера, получает `nested_worker_depth_exceeded`, и новый Run глубину не
сбрасывает.

Не редактируй файлы, принадлежащие воркеру: находка ревью становится отдельной задачей тому же
или новому воркеру.

## Когда применять

Для независимой или слабо связанной работы с отдельным ревью каждого заметного изменения.
Максимум два одновременных воркера. Не распараллеливай связанные сбои, общее состояние,
пересекающиеся файлы или разведочную отладку, где ещё не ясно, что сломано — сначала диагноз
или границы.

## Бриф и запуск

Подготовь один самодостаточный бриф из
[../dispatching-codex-workers/templates/initial-brief.md](../dispatching-codex-workers/templates/initial-brief.md):
точный `Target`, один `Change`, `Constraints`, `Ownership`, наблюдаемое `Acceptance`. Если бриф
класса С/В опирается на допущения о существующем коде — сначала сверь их по
[../../methodology/plan-vs-code.md](../../methodology/plan-vs-code.md).

```text
orca orchestration run-create --objective "[цель]" --json
~/.claude/bin/ws --spec @[путь к файлу брифа] --worktree current --agent codex --model [id] --effort [level] --json
```

Запуск идёт через `ws`, а не напрямую через `orca orchestration worker-start`, — иначе гейт
триггеров (`high:`/`astra:`/`opus:`/`legacy:`) не сработает. Передавай `--model` и `--effort`
явно для каждого нового агента и сверяй `launch.effective` в ответе — это фактически применённые
значения, а не то, что было запрошено. Правила выбора модели и таблица тиров —
в [../../methodology/model-routing.md](../../methodology/model-routing.md).

## Приём отчёта

`--outcome succeeded|failed` обязателен, но не заменяет содержательный статус — он передаётся
первой строкой тела `worker_done`.

| Статус | Действие координатора |
| --- | --- |
| `DONE` | Проверь Acceptance; для заметного изменения — независимое первое ревью. |
| `DONE_WITH_CONCERNS` | Проверь риски; либо прими явно, либо назначь точечную доработку. |
| `NEEDS_CONTEXT` | Передай недостающие факты или решение, продолжи тем же терминалом. |
| `BLOCKED` | Разбери причину; не повторяй идентичную попытку без изменения входа. |

Вопрос воркера через `orca orchestration ask` — только для неоднозначности, способной изменить
поведение. Ответь по ID сообщения:

```text
orca orchestration reply --id [msg_id] --body "[ответ]" --json
```

Освобождай воркер только после принятого завершённого Dispatch:

```text
orca orchestration worker-release --dispatch [dispatch_id] --json
```

## Ревью и доработка

Первое ревью — полный список находок по
[../dispatching-codex-workers/templates/first-review-brief.md](../dispatching-codex-workers/templates/first-review-brief.md),
со строкой `review-of: [dispatch id автора]`. Доработка —
по [../dispatching-codex-workers/templates/remediation-brief.md](../dispatching-codex-workers/templates/remediation-brief.md)
с отчётом по каждой находке. Повторное ревью — только дельта,
по [../dispatching-codex-workers/templates/re-review-brief.md](../dispatching-codex-workers/templates/re-review-brief.md).
После второго `FAIL` — стоп и решение человека, не третий круг. Подробности —
в [../../methodology/review-loops.md](../../methodology/review-loops.md).

## Минимальный цикл

1. Бриф, Run, выбор модели, запуск одного-двух независимых воркеров.
2. Приём `worker_done`, ответы на вопросы, подтверждение доставки.
3. Для заметного изменения — независимое первое ревью соразмерной моделью.
4. Доработка и дельта-ревью по правилам кругов, стоп после второго `FAIL`.
5. `worker-release` только после принятого результата.
