# Делегирование Codex-воркерам (координатор — Claude Code)

> Вариант для тех, у кого координатором выступает Claude Code, а исполнителями — Codex-воркеры.
> Если координирует сама Codex-сессия, используйте [SKILL.md](SKILL.md): механики те же,
> но роль и команды описаны под неё, и там разобран лимит вложенности воркеров.
> Шаблоны брифов в `templates/` общие для обоих вариантов.

Координатор декомпозирует независимую работу, выдаёт каждому воркеру самодостаточный бриф и принимает результат через Orca. Не передавай историю разговора вместо требований: решение, интерфейсы, границы и критерии приёмки должны быть в брифе.

## Когда применять

Используй для плана с независимыми или слабо связанными кусками реализации и отдельным ревью каждого заметного изменения. Максимум два одновременных воркера.

Не распараллеливай, если:

- сбои связаны: сначала исследуй их вместе;
- нужен полный контекст системы;
- это разведочная отладка и ещё неясно, что сломано;
- есть общее состояние, общие ресурсы или пересекающиеся файлы.

В этих случаях сначала вынеси диагноз, границы или последовательность работы, затем делегируй независимые части.

## Подготовка и запуск

1. Зафиксируй базовый SHA и подготовь один бриф из [templates/initial-brief.md](templates/initial-brief.md). В нём обязательны `Target`, `Change`, `Constraints`, `Ownership`, `Acceptance`.
2. Создай Run и явно выбери модель и effort. Не опускай `--model`: иначе воркер наследует дорогой дефолт.

```text
orca orchestration run-create --objective "[цель]" --json
orca orchestration worker-start --spec "[путь или текст брифа]" --worktree current --agent codex --model [id] --effort [level] --json
```

3. Жди сообщения, обрабатывай вопросы через reply и освобождай только принятый завершённый Dispatch.

```text
orca orchestration check --wait --types "worker_done,escalation,question" --timeout-ms [N] --json
orca orchestration reply --id [msg_id] --body "[ответ]" --json
orca orchestration worker-release --dispatch [dispatch_id] --json
```

`worker_done` обязан иметь `--outcome succeeded|failed`; рабочий статус передаётся первой строкой тела. Не считай `--outcome` заменой содержательной оценки.

## Выбор модели

Бери наименее мощную модель, которая справится. Хороший бриф уменьшает требуемый класс модели: большинство задач реализации механические, если постановка полная.

| Работа | Модель |
| --- | --- |
| Механическая реализация по хорошо составленной спеке | `gpt-5.6-luna` |
| Обычная реализация или ограниченное исследование с суждением | `gpt-5.6-terra` |
| Сложная реализация, неоднозначное расследование, первое ревью крупной работы | `gpt-5.6-sol` |
| Особо требовательная архитектура или критическое ревью | `gpt-6-astra` |

## Приём отчёта

Проверь первую строку тела `worker_done`, затем применяй правило:

| Статус | Действие координатора |
| --- | --- |
| `DONE` | Проверь acceptance и подготовь независимое ревью, если оно требуется. |
| `DONE_WITH_CONCERNS` | Проверь названные риски; либо прими их явно, либо оформи точечную доработку. |
| `NEEDS_CONTEXT` | Передай недостающие факты, решение или доступ; затем продолжи тем же терминалом. |
| `BLOCKED` | Разбери причину по правилам ниже; не перезапускай идентичную попытку. |

## Вопросы воркера

Если воркеру не хватает факта или решения, он задаёт вопрос через `orca orchestration ask`. Получив вопрос, вынеси решение и ответь по ID сообщения:

```text
orca orchestration reply --id [msg_id] --body "[решение]" --json
```

Граница механики: вопрос уместен только для неоднозначности, способной изменить поведение или выйти за границы задачи. Подтверждать однозначный бриф не нужно — в брифе прямо скажи, что начинать надо без запроса подтверждения. Вопрос вида «подтвердите старт» стоит круга переписки и ничего не проверяет.

После ответа проверь, не изменился ли scope, прежде чем запускать следующую работу.

## Разбор затыка

Никогда не перезапускай ту же модель без изменения входных условий.

| Причина | Следующее действие |
| --- | --- |
| Не хватило контекста | Добавь конкретные факты в бриф; оставь ту же модель. |
| Не хватило рассуждения | Передай прежние факты и назначь модель на тир выше: luna → terra → sol → astra. |
| Задача велика | Разбей на независимые задачи с отдельными ownership и acceptance. |
| План неверен | Координатор принимает и фиксирует решение, затем передаёт его с новой задачей. |

Не подменяй диагноз предположением: если причина не доказана, исследуй её как одну задачу до нового запуска.

## Доработка и повторное ревью

После первого ревью собери конкретные находки и базовый SHA дифа. Для доработки используй [templates/remediation-brief.md](templates/remediation-brief.md).

- Круги 1–3: переиспользуй терминал исходного воркера, не поднимая контекст заново:

```text
orca orchestration worker-start --task [new_task_id] --terminal [handle] --json
```

  `--model` и `--effort` с `--terminal` не сочетаются: класс модели зафиксирован стартом того воркера. Для кругов 1–3 это нормально — доработка по готовому списку находок механическая. Если посреди кругов стало ясно, что нужен класс выше, переиспользование не годится: запускай свежего воркера с явной моделью.

- Круг 4+: запусти свежего воркера моделью на тир выше и с брифом, содержащим историю находок.
- После второго вердикта `FAIL` останови циклы и эскалируй пользователю; третий круг не запускай.

Повторное ревью — только дельта, не полный проход. Дай ревьюеру из [templates/re-review-brief.md](templates/re-review-brief.md) список исходных находок и diff от SHA прошлого ревью; модель — `gpt-5.6-terra`. Scope, зафиксированный первым ревью, не расширяй: новые находки оформляй отдельной задачей.

## Минимальная последовательность

1. Сформулируй бриф, зафиксируй SHA, выбери модель и запусти одного или до двух независимых воркеров.
2. Прими `worker_done` по статусу и проверь acceptance.
3. Запусти первое ревью соразмерной моделью; для крупной работы — `gpt-5.6-sol`.
4. При находках проведи доработку и точечное re-review по правилам кругов.
5. После принятого результата освободи Dispatch через `worker-release`.
